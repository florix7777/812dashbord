## Текущее состояние проекта

Проект переведен на **API Mode** - данные хранятся в PostgreSQL и передаются через backend API.

```

│   Nginx     │────▶│  FastAPI    │────▶│ PostgreSQL  │

└─────────────┘     └─────────────┘     └─────────────┘
       │                   │
       ▼                   ▼
┌─────────────┐     ┌─────────────┐
│   HTML/JS   │     │ auto_updater│

└─────────────┘     └─────────────┘
```

## Обновление (стабилизация, продолжение)

**Дата:** 2026-08-21

### Что исправлено

1. **Добавлен сервис `updater` в docker-compose.yml.**
   Раньше `auto_updater.py` нигде не запускался автоматически — файлы, загруженные
   через `/api/upload/xlsx|pdf`, просто лежали в `reports/` и никто их не парсил.
   Теперь это отдельный контейнер (`Dockerfile.updater` + `requirements-updater.txt`),
   который постоянно смотрит на `reports/` через watchdog и при появлении нового
   файла: парсит → пишет в Postgres → обновляет `assets/js/data.js` (fallback).
   Это и есть настоящий "единый источник истины": Postgres — истина, statics — резерв.

2. **Frontend подключён к живым данным.**
   Добавлен `assets/js/data-loader.js`, который выполняет синхронный запрос к
   `GET /api/metrics` до инициализации `app.js` и подменяет `DASHBOARD_DATA`
   на актуальные данные из базы. Подключён только на `analytics.html`,
   `forecast.html`, `rating.html` — страницах, которые реально показывают
   метрики сотрудников. Тактические страницы (`instruments.html`, `law.html`,
   `manual.html`, `objections_*.html`) НЕ тронуты и остаются без fetch(),
   как того требовал предыдущий handoff.
   Если API недоступен — страница тихо остаётся на статике из `data.js`,
   ничего не ломается.

### Важный незакрытый пункт (сознательно не трогали в этот раз)

**Аутентификации на API до сих пор нет** (`allow_origins=["*"]`, все `/api/*`
открыты). Это было и раньше в известных ограничениях. Пока фронтенд — просто
статические HTML-страницы без логина, единственный реалистичный вариант защиты —
либо Basic Auth на уровне nginx (закрывает всё сразу, 20 минут работы), либо
полноценный логин с JWT (требует отдельной сессии работы над UI входа).
Раз в системе крутятся реальные оценки сотрудников — прежде чем выкладывать на
публичный VPS, это стоит закрыть в первую очередь после сегодняшних правок.

## Обновление (закрыт доступ / авторизация)

**Дата:** 2026-08-21 (продолжение)

### Что исправлено

1. **Basic Auth на весь сайт.** nginx теперь требует логин/пароль (`.htpasswd`,
   не в git) на все страницы и на `/api/`. Инструкция генерации пароля —
   в `RUNBOOK.md` → "Доступ и пароли". Без `.htpasswd` сборка `nginx`
   специально падает, чтобы никто не выложил дашборд без пароля по ошибке.

2. **Postgres и backend больше не торчат в интернет.** Убраны `ports: 5432:5432`
   и `ports: 8000:8000` из docker-compose.yml. Раньше это значило, что даже
   с паролем на сайте, любой человек с адресом VPS и портом мог напрямую
   достучаться до базы данных или до API в обход всей защиты. Теперь оба
   сервиса доступны только внутри docker-сети (другим контейнерам), снаружи —
   только через nginx на 80-м порту.

### Осталось на будущее (не критично прямо сейчас)

- CORS на backend (`allow_origins=["*"]`) можно сузить, но раз backend больше
  не достижим напрямую — реального риска это уже не несёт.
- Basic Auth — это один общий пароль на всех. Если понадобится разделять,
  кто что видит (например, тимлид видит только свою команду) — это уже
  полноценный логин с ролями, отдельная задача.

## Обновление (реальный аудит вместо "похоже, работает")

**Дата:** 2026-08-21 (продолжение, "довести до идеала")

Прогнал существующий CI-набор проверок вручную (pytest, bandit, frontend
security guard, компиляция) — раньше их никто не запускал после последних
правок, и часть уже была красной незаметно для всех. Нашёл и закрыл:

1. **Хранимый XSS через отчёты.** `tendencies`/`rec` (свободный текст из PDF)
   и имена сотрудников вставлялись в `innerHTML` без экранирования в 7 местах
   `assets/js/app.js`. Плюс 4 места собирали имя сотрудника прямо в атрибут
   `onclick="showEmployee('...')"` — экранировался только одинарный апостроф,
   двойные кавычки/спецсимволы могли выйти за пределы HTML-атрибута.
   Добавил `escapeHtml()`/`escapeHtmlWithBreaks()`, все 11 мест исправлены;
   `onclick` теперь без интерполяции вообще — значение идёт через
   `data-emp-name` (экранированный HTML-атрибут) + `this.dataset.empName`.
   Эталон в `security/frontend-security-baseline.json` обновлён осознанно,
   после полного ручного аудита каждого использования `innerHTML`.

2. **Бесконечный цикл в `auto_updater.py`.** `refresh_dashboard()` при каждом
   срабатывании звал `sync_reports_to_backend()`, которая переотправляла ВСЕ
   xlsx/pdf файлы обратно на backend по HTTP. backend сохранял их в ту же
   папку `reports/`, которую слушает watchdog → это заново триггерило
   `refresh_dashboard()` → снова переотправка → бесконечно. Раньше это было
   незаметно, потому что `updater` вообще не был подключён к docker-compose.
   Теперь, когда я его подключил (с общим томом `reports/` с backend), баг
   стал бы реальным сразу после первого файла. Убрал вызов из горячего пути,
   функция осталась для редкого сценария (backend на отдельном хосте без
   общего тома) — только для ручного вызова, с явным предупреждением в коде.

3. **Устаревший `@app.on_event("startup")`** заменён на современный `lifespan`
   (убрал deprecation warning, тесты проходили с предупреждением раньше).

4. **CORS отключён совсем** (было `allow_origins=["*"]` + `allow_credentials=True`
   — невалидная и небезопасная комбинация). Frontend и backend теперь на одном
   origin через nginx, кросс-доменный доступ не нужен. Включается явно через
   `ALLOWED_ORIGINS` в `.env`, если когда-нибудь понадобится.

5. **Загрузка файлов ужесточена**: проверка реальной сигнатуры файла (не
   только расширения — переименованный `.exe` в `.xlsx` больше не пройдёт),
   лимит размера `MAX_UPLOAD_BYTES` (20 МБ по умолчанию, настраивается),
   защита от path traversal в имени файла.

6. **Удалён мёртвый `/api/process-reports`** — ничего не делал, только вводил
   в заблуждение, что "обработка" — отдельный шаг. RUNBOOK.md переписан под
   актуальный процесс (просто положить файл — обработается само).

## Обновление (первые фичи по SVP heatmap и рейтингу)

**Дата:** 2026-08-21 (переход к фичам)

### Что добавлено и реально работает

1. **Подсказка "сколько звонков до нормы/максимума"** на обеих тепловых картах
   (Heatmap и Pro). Наведение на ячейку критерия теперь показывает не только
   диагноз, но и: сколько ещё звонков подряд на 100% нужно, чтобы средний
   балл по этому критерию дошёл до нормы (75% — тот же порог, что уже
   используется в бейдже "Цель достигнута"), и отдельно — до практического
   максимума (99%). Считается по формуле от фактического среднего и
   количества звонков за период (`activity_count`), честно, не рандом.

   Важная деталь, которую стоит знать: ровно **100%** математически
   недостижимы, пока в истории есть хоть один неидеальный балл — поэтому
   показываю не "100%", а "99%" (в подсказке явно так и написано). Это не
   баг, а следствие того, как считается среднее.

2. **"До первого места" + "кто догоняет"** — в карточке сотрудника
   (клик по строке в heatmap/рейтинге) теперь видно: его место в общем
   рейтинге по TQS, разрыв до лидера (с именем лидера), и кто идёт следом
   и на сколько процентных пунктов отстаёт (с подсветкой красным, если
   разрыв мал — то есть могут обогнать в любой момент).

### Что НЕ сделано — осознанно, а не забыто

**Взыскание (сумма собранного долга) — этого поля вообще нет в модели
данных дашборда.** Ни в `data.js`, ни в парсинге `auto_updater.py`, ни в
таблице Postgres `employee_scores`. Всё, что сейчас есть про взыскание —
это текстовые упоминания в рекомендациях QC (ссылки на статьи закона),
не числовые метрики сбора денег. Чтобы сделать тепловую карту и рейтинг
по взысканию (как просили), нужно:

- Завести отдельный источник данных — судя по присланным ранее скриншотам,
  это отдельный Excel-отчёт от тимлидов ("Сбор, UZS", "% выполнения плана"),
  не тот же файл, что парсит `auto_updater.py` сейчас.
- Добавить парсинг этого формата, новую таблицу/колонки в Postgres.
- Добавить взыскание в `getRankContext()` как вторую метрику рейтинга
  (сейчас там только TQS).
- Отрисовать отдельную тепловую карту по взысканию, по аналогии с SVP.

Это отдельный, самостоятельный кусок работы — не спрятанный баг, а честно
нереализованная часть запроса, которую стоит делать следующим шагом.

## Обновление (дизайн-система: этап 1 — единая палитра и типографика)

**Дата:** 2026-08-25 (переход к дизайну, по плану "сначала система, потом глубже по страницам")

### Направление

Ушли от двух самых típичных ИИ-дефолтов, в которых жило приложение
одновременно (тёмная тема = почти чёрный + оранжевый; светлая тема = кремовый
+ оранжевый). Новое направление — рабочая консоль контроля: два акцента с
чёткой ролью, а не один декоративный:

- **Латунь** (`#C0913F` / `#9C7530`) — "официальный/аудиторский" акцент:
  бейджи, бренд, ранг №1, ключевые метки. Ссылается на суть инструмента —
  это оценка по регламенту со ссылками на статьи ГК РУз, а не просто дашборд.
- **Сигнальный циан** (`#3FA7C9` / `#7CC9E0`) — "живой/активный" акцент:
  активные пункты меню, ссылки, главные метрики (TQS и т.п.).
- Семантика результатов (зелёный/жёлтый/красный для баллов) **не тронута** —
  она и так функциональна, менять её смысл было бы вредно для тех, кто

### Важная находка по пути — реальный баг в уже отгруженном коде

При тестировании CRM-парсера всплыла ошибка: колонка "Оператор" не находилась,
хотя явно присутствовала в файле. Причина — классическая ловушка Python:
```
name_idx = _find_column(columns, "оператор") or _find_column(columns, "сотрудник")
```
Если "Оператор" — самая первая колонка (индекс `0`), то `0 or X` в Python
возвращает `X`, а не `0`, потому что `0` считается ложным значением. То есть
код тихо пропускал правильный ответ и пытался найти следующий маркер.

**Это тот же самый паттерн уже был в парсере взыскания**, отгруженном
раньше — просто не проявился, потому что в тестовом файле "Оператор" не
был первой колонкой (повезло). Если бы в реальном файле от тимлидов
"Оператор" стоял первым — взыскание тихо не находило бы имена сотрудников,
без единой ошибки в логах.

Исправлено в обоих местах: добавлена функция `_find_first_column()`,
которая явно проверяет `is not None`, а не полагается на `or`. Перепроверил
тестами специально с "Оператор" на нулевой позиции для обоих парсеров —
оба теперь работают верно.
