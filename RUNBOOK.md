## Быстрый старт

### Требования

- Docker и Docker Compose
- Python 3.11+ (для локальных скриптов)
- `openssl` (для генерации пароля Basic Auth — есть почти на любом Linux/Mac из коробки)

### Запуск проекта

```bash
# 1. Клонировать репозиторий
git clone <repository-url>
cd Dashboard_SC

# 2. Создать .env из примера
cp .env.example .env

# 3. Отредактировать .env (изменить пароли при необходимости)
nano .env

# 4. Создать пароль для входа на дашборд (Basic Auth, см. также .htpasswd.example)
openssl passwd -apr1 'ВАШ_ПАРОЛЬ'
# скопируйте вывод (строка вида $apr1$....) и создайте файл:
echo 'admin:ВСТАВЬТЕ_ХЭШ_СЮДА' > .htpasswd
# .htpasswd в .gitignore — он не попадёт в git, это нормально и обязательно

# 5. Запустить проект
docker compose up -d --build

# 6. Проверить статус
docker compose ps

# 7. Открыть в браузере (спросит логин/пароль — тот, что вы задали в п.4)
# Frontend: http://localhost/
# API health (через nginx, напрямую порт 8000 больше не торчит наружу):
# http://localhost/api/health
```

> Без файла `.htpasswd` шаг `docker compose up -d --build` упадёт на сборке
> `nginx` — это ожидаемо и специально, чтобы никто случайно не поднял дашборд
> без пароля.

### Остановка проекта

```bash
docker compose down

# Полная очистка (включая volumes)
docker compose down -v
```

### Доступ и пароли

- Логин на сайт — Basic Auth уровня nginx, файл `.htpasswd` (не в git).
- Добавить ещё одного пользователя — добавить ещё одну строку `логин:хэш` в `.htpasswd` и `docker compose up -d --build nginx` (пересобрать только nginx).
- Забыли пароль — просто сгенерируйте новый хэш командой из шага 4 и перезапишите `.htpasswd`.
- `postgres` (5432) и `backend` (8000) больше не открыты наружу — доступны только другим контейнерам внутри docker-сети. Прямой доступ к базе — через `docker compose exec postgres psql -U qc_user -d qc_dashboard`.

## Конфигурация

### Переменные окружения (.env)

| Переменная | Описание | Пример |
|------------|----------|--------|
| `POSTGRES_USER` | Пользователь PostgreSQL | `qc_user` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL | `change_me` |
| `POSTGRES_DB` | Имя базы данных | `qc_dashboard` |

## Обновление данных (API Mode — текущий режим)

Проект работает в **API Mode**: Postgres — источник истины, `assets/js/data.js` —
только резервная копия на случай, если backend временно недоступен.

### Как это работает

Контейнер `updater` (сервис в docker-compose.yml, процесс `auto_updater.py`)
постоянно следит за папкой `reports/`. Как только там появляется новый файл —
он сам парсит его и пишет результат в Postgres, а заодно обновляет
`assets/js/data.js` как резерв. Отдельно "запускать обработку" не нужно —
это происходит автоматически, в течение нескольких секунд после появления файла.

### Способ 1 — просто положить файл в папку (самый простой)

```bash
cp "Quality_Июль_2026.xlsx" reports/
cp "Итог_отч_по_сотр_SC_июль_2026.pdf" reports/
# всё, updater сам заметит и обработает — смотрите логи:
docker compose logs -f updater
```

### Способ 2 — через сайт (форма загрузки на странице аналитики)

Загруженный через UI файл сохраняется в ту же папку `reports/`, дальше
всё точно так же подхватывается `updater` автоматически.

### Способ 3 — через API вручную (например, для скриптов/автоматизации)

Обратите внимание: `/api/*` теперь закрыт Basic Auth и доступен только
через nginx (порт 80), прямой доступ к backend на 8000 отключён:

```bash
curl -u admin:ВАШ_ПАРОЛЬ -X POST -F "file=@reports/Quality_01.04.2026.xlsx" \
  http://localhost/api/upload/xlsx

curl -u admin:ВАШ_ПАРОЛЬ -X POST -F "file=@reports/Отчет.pdf" \
  http://localhost/api/upload/pdf
```

Лимит на размер файла — 20 МБ (настраивается через `MAX_UPLOAD_BYTES` в `.env`).
Файлы с неверным содержимым (например, переименованный `.exe` в `.xlsx`)
будут отклонены на уровне сигнатуры файла, не только по расширению.

### Взыскание (раздел "Взыскание" в меню) — ежедневная загрузка

Это отдельный, независимый источник данных от QC-оценок звонков. Файл
распознаётся автоматически по заголовкам колонок — не по имени файла.

**Формат файла:** обычный XLSX с колонками (порядок неважен, важны только
подстроки в названиях):
- `Оператор` (или `Сотрудник`) — ФИО, как в остальной системе
- `Сбор` — сумма взыскано, накопительным итогом с начала месяца на дату отчёта
- `План ...` — план на месяц (например "План Июль 2026")

**Как назвать файл:** обязательно включите дату в любом из форматов —
`Взыскание_21.08.2026.xlsx`, `Sbor-21-08-2026.xlsx`, `2026-08-21_sbor.xlsx`.
Дата нужна, чтобы система знала, за какой день этот снимок — без неё будет
использована дата изменения файла (менее надёжно, могут быть расхождения
при пересылке через мессенджеры).

**Куда класть:** так же, как QC-отчёты — просто `reports/`, или через форму
загрузки на сайте. Апдейтер сам поймёт, что это отчёт по взысканию, а не
QC-оценки, и обработает отдельно. Повторная загрузка файла с той же датой
перезапишет данные за этот день, а не задублирует.

**Что считается автоматически:** место в рейтинге, % выполнения плана,
тренд к вчерашнему дню (▲/▼), сравнение с тем же днём/итогом прошлого
месяца — всё видно на странице "Взыскание".

### CRM-действия — ежемесячная загрузка

Третий независимый источник данных (не связан с QC-оценками и взысканием).
Тоже распознаётся автоматически по заголовкам колонок.

**Формат файла:** одна строка = один оператор, каждая колонка — отдельный
тип действия с числом за него. Например: `Оператор`, `Обещание платежа`,
`Отказ от оплаты`, `Думает`, `Заявленный платеж`, `Бросил трубку`,
`Отказ от разговора`, `Тишина`. Список категорий не жёстко зашит —
можно добавлять/убирать колонки, система подхватит любые.

**Как назвать файл:** включите месяц в любом из форматов — `CRM_08.2026.xlsx`,
`CRM-действия_Август_2026.xlsx` (главное — есть `MM.YYYY`, `DD.MM.YYYY`
или `YYYY-MM` где-то в имени). Без этого возьмётся месяц по дате изменения
файла.

**Куда класть:** туда же, `reports/`, или через форму на сайте — апдейтер
сам отличит этот формат от QC-отчётов и от взыскания. Повторная загрузка
за тот же месяц перезапишет данные, а не задублирует.

**Где смотреть:** круговая диаграмма в карточке сотрудника (клик по имени
на странице "Рейтинг") — показывает разбивку CRM-действий за выбранный
месяц.

### Если Postgres временно недаёт данных

Фронтенд (`analytics.html`, `rating.html`, `forecast.html`) автоматически
откатится на статический `assets/js/data.js` — сайт не сломается, просто
покажет последние сохранённые данные вместо самых свежих. После изменения
`data.js` вручную (Static Mode fallback) нужно пересобрать `nginx`:
```bash
docker compose build nginx
docker compose up -d nginx
```


### Генерация tactical-data.js

При изменении контента в `content/`:

```bash
python scripts/build_tactical_data.py
```

## Бэкапы и восстановление

### Бэкап PostgreSQL

```bash
# Создать бэкап
docker exec qc_postgres pg_dump -U qc_user qc_dashboard > backup_$(date +%Y%m%d).sql

# Сжать бэкап
gzip backup_$(date +%Y%m%d).sql
```

### Восстановление из бэкапа

```bash
# Распаковать (если сжат)
gunzip backup_20260508.sql.gz

# Восстановить
docker exec -i qc_postgres psql -U qc_user qc_dashboard < backup_20260508.sql
```

### Бэкап данных dashboard

Данные хранятся в PostgreSQL. Для экспорта в JSON:

```bash
# Через API (работает только после начала накопления данных в PostgreSQL при ENABLE_BACKEND_SYNC=1)
curl http://localhost:8000/api/metrics > dashboard_backup_$(date +%Y%m%d).json
```

## Диагностика

### Проверка состояния

```bash
# Health check API
curl http://localhost:8000/api/health

# Проверка контейнеров
docker compose ps

# Проверка логов
docker compose logs -f nginx
docker compose logs -f backend
docker compose logs -f postgres
```

### Интерпретация health check

| Статус | Database | Описание |
|--------|----------|----------|
| 200 | connected | Все работает |
| 200 | not_configured | DATABASE_URL не задан |
| 503 | error | Ошибка подключения к БД |

### Просмотр данных в БД

```bash
# Подключиться к PostgreSQL
docker exec -it qc_postgres psql -U qc_user qc_dashboard

# Посмотреть таблицы
\dt

# Посмотреть данные
SELECT employee_name, month, period, tqs FROM employee_scores ORDER BY created_at DESC LIMIT 10;

# Выйти
\q
```

### Отладка auto_updater.py

```bash
# Запустить с подробным выводом
python -u auto_updater.py

# Проверить синтаксис
python -m compileall auto_updater.py
```

## Частые проблемы

### Контейнеры не запускаются

```bash
# Проверить логи
docker compose logs

# Пересоздать контейнеры
docker compose down
docker compose up -d --build
```

### Ошибка подключения к БД

1. Проверьте `.env`:
```bash
cat .env | grep DATABASE_URL
```

2. Убедитесь, что PostgreSQL запущен:
```bash
docker compose ps postgres
```

3. Проверьте логи PostgreSQL:
```bash
docker compose logs postgres
```

### Данные не обновляются

1. Проверьте права на папку `reports/`:
```bash
ls -la reports/
```

2. Проверьте логи auto_updater:
```bash
# Запуск auto_updater происходит локально в терминале
# Смотрите вывод в терминале. Контейнер auto_updater в docker-compose не предусмотрен.
```

3. Убедитесь, что файлы соответствуют ожидаемому формату:
   - XLSX: лист "Оценки звонков Soft Collection"
   - PDF: содержит "Отчет по сотруднику"

### Frontend не показывает данные

1. Проверьте API:
```bash
curl http://localhost:8000/api/metrics
```

2. Проверьте консоль браузера (F12) на ошибки

3. Убедитесь, что nginx запущен:
```bash
docker compose ps nginx
```

### Сброс проекта к начальному состоянию

```bash
# Полная очистка
docker compose down -v

# Удалить все данные
rm -rf reports/*.xlsx reports/*.pdf

# Запустить заново
docker compose up -d --build
